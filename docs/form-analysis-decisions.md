# 운동 뒤 자세 분석(스쿼트) 진행 중 내린 판단

- 기간: 2026-11-24
- 브랜치: `feat/form-analysis` (`main` 위)
- 설계: `docs/specs/2026-11-24-form-analysis-design.md` (정확도 수치 요약은 10절)
- 계획: `docs/superpowers/plans/2026-11-24-form-analysis.md`
- 이 문서는 작업 중 진행 장부(git 제외)에 있던 판단 기록과 작업별 보고의 실기기 확인 항목을 옮긴 것이다.
- 개인 녹화 데이터는 이 저장소에 올리지 않으므로 여기에도 옮기지 않았다.

## 1. 사용자가 정한 것
- 지적은 운동이 끝난 뒤 결과 화면에서 보여 준다(운동 중 실시간 지적은 하지 않는다).
- 지적한 구간은 실제 영상으로 다시 볼 수 있다(반복 재생, 관절 선 겹치기).
- 루틴마다 최근 3회 기록은 영상 전체를 보관하고, 오래된 기록은 지적 구간만 남긴다.
- 촬영은 45도 각도로 한다.
- 신발은 평소 신던 대로 신는다.
- 바른 자세를 미리 등록하지 않는다. 절대 기준과 내 기록 대비 상대 기준을 함께 쓴다.
- 자세 모델은 RTMPose-m을 쓴다.
- 학습 데이터 동의와 맞아요/틀려요 투표, 직접 라벨을 넣는다. 동의한 기록만 JSONL로 내보낸다.
- 목표는 배포를 신경 쓰지 않는 실험용 파인튜닝이다.
- 의존성 두 개 설치를 허락했다(2026-11-24): `onnxruntime-web@1.20.1`, `@capacitor/filesystem@^8.1.5`.
- 일은 서브에이전트에게 맡기고, 작업마다 리뷰를 거친다.

## 2. 구현하면서 대신 내린 판단 (틀렸을 때의 비용)
| 판단 | 이유 | 틀렸을 때 |
|---|---|---|
| R1: 분석 대기열은 세션에서 SetLog(반복 시각)를 못 찾으면 그 key를 대기열 뒤로 보내 1초 뒤 다시 시도하고, 5번 안 되면 포기한다(다음 resumePending 때 다시) | 엔진의 중간 저장이 비동기라서 세트 끝 알림이 저장보다 먼저 올 수 있다 | 분석이 늦게 시작될 뿐이다 |
| R2: 반복 시각이 없는 옛 기록의 영상은 분석 결과를 저장하지 않고 건너뛴다 | 옛 기록에는 영상이 없어서 실제로는 생기지 않는다(설계 8.5 호환) | 없음 |
| R3: 길이 이상치 필터는 세트 전체 중앙값이 아니라 시간상 이웃(±200ms) 프레임 중앙값 대비 30%로 본다 | 45도 촬영에서는 앉을수록 2D 허벅지가 자연스럽게 짧아져서 바닥 프레임을 잘못 버렸다 | 천천히 틀어지는 인식 오류를 못 거른다 |
| R4: oneLeg는 "한쪽 무릎 150° 초과(거의 폄)이고 다른 쪽 120° 미만"일 때만 | 45도에서는 가까운 다리와 먼 다리의 2D 각도 차이가 80°까지 난다. 발 옮기기만 잡는 것이 설계 취지다 | 한쪽으로 쏠린 스쿼트가 판정에 들어간다 |
| R5: 발 점(엄지발가락·뒤꿈치)은 최소 점수를 0.15로 낮추고 발마다 따로 계산해 유효한 발만 평균한다 | 45도에서 먼 발의 점수가 내내 0.24~0.33이라 0.3 필터가 뒤꿈치 든 프레임을 버렸다 | 흐린 발 점이 섞여 잡음이 늘어난다 |
| R6: rtmposeOrt는 처음 쓰는 곳(분석 대기열)에서 동적 import로 불러오고, 중복 ORT wasm(약 21MB)은 vite 플러그인으로 빼서 별도 청크로 둔다 | 정적으로 import하면 쓰지 않는 wasm이 dist에 한 번 더 들어간다 | APK가 21MB 커진다(작업 12에서 확인해 없음) |
| R7: `SetCapture.beginSession`은 `{sessionId, routineId}`만 받고, capture가 스스로 설정을 읽어 captureMeta(동의 버전 등)를 저장한다. 영상 사용이 꺼져 있으면 녹화하지 않는다 | 엔진이 설정을 알 필요가 없게 한다 | 위치만 옮기면 된다 |
| R8: 세트 제목은 설계 6.1처럼 "{운동 이름} {n}세트  {횟수}회  ✓ 목표 달성"(목표 달성은 endReason이 target일 때), 지적 줄 앞 ⚠, 세트 요약 줄 앞 ⓘ | 설계가 기준이다 | 문구 조정뿐이다 |
| 분석은 한 번에 한 세트, 프레임은 직렬로 estimate한다. 다음 세트가 시작되면 멈추고 쉬는 시간에 다시 돈다 | 실시간 세기가 밀리지 않게 하고, 공유 canvas는 동시 호출이 안 된다 | 분석이 늦어진다 |
| 분석 실패(failed)는 저장해 두고 자동 재시도하지 않는다 | 같은 실패를 매 실행마다 반복하지 않기 위해서다 | 일시적 오류도 영구 실패로 남는다(다시 분석 UI 없음) |
| `planRetention`에 5번째 인자(영상 시작 시각 Map)를 추가했다. 분석 전 세트는 정리하지 않는다 | 영상 안 ms를 계산하려면 영상 시작 시각이 필요하고, 분석 전 세트를 지우면 결과를 못 낸다 | 정리가 한 번 늦어진다 |
| 웹 다운로드는 objectURL을 click 직후 바로 revoke한다. Android 내보내기는 Documents에 쓰고 실패하면 앱 전용 폴더로 폴백한다 | 브리프 지시이고, Android 10+에서 Documents 쓰기는 기기별로 실패할 수 있다 | 일부 브라우저에서 다운로드가 끊긴다. 폴백이면 adb 경로가 다르다 |
| `APP_VERSION`은 상수 `'0.0.0'`으로 둔다 | 내보내기 헤더에 넣을 값이 필요했다 | 수동으로 맞춰야 한다 |
| 선택한 의존성 설치 외에는 새 패키지를 넣지 않았다. ORT·모델 파일은 로컬에서 복사하고 커밋하지 않는다 | 허락받은 범위를 지킨다 | — |
| PC 자가 점검에 RTMPose 세션 생성 항목을 추가하고 판정에 넣었다(`selftest.ts`, `electron/main.ts`) | 설계 12절 통합 확인. 외부 요청 0건 판정은 그대로다 | PC 우선순위가 낮아 Electron에서 실제로 돌려 보지 않았다(타입·빌드만 통과) |

## 3. 나중으로 미룬 사소한 것
- 저장 구조(작업 3)
  - IndexedDB `openDB`에 blocked/blocking 콜백이 없다(옛 버전 탭이 열려 있을 때).
  - key 사전순 정렬이라 `s1/0/10`이 `s1/0/2`보다 앞이다.
  - dbPromise reject가 영구 캐시된다(기존 문제).
  - usageBytes가 커서 순회다.
- 판정(작업 1·2)
  - 옛 세션 테스트가 copyLog의 reps 없는 분기를 타지 않는다. 버티기 `reps: []` 테스트가 없다.
  - button 테스트가 undo 동작을 가정한다.
  - 점수 필터 테스트가 약하다. 상대 기준 비교군에 이미 지적된 반복이 들어가 민감도가 떨어진다.
  - 자기 제외가 객체 동일성에 기댄다. frames가 시간순이어야 한다는 전제가 문서에 없다. enabled 조합 테스트가 없다.
- 모델·녹화(작업 4·5)
  - `getContext`가 null일 때 처리가 없다. 0 크기 상자는 호출부에서 거른다.
  - CSP의 `/form/ort/` 동적 import는 기기에서 확인한다(4절).
  - `onSaved` 예외가 나면 저장됐는데 null이 반환된다(작업 6에서 try/catch로 감쌈).
  - startedAt을 `start()` 직전에 잡아 수십 ms 어긋난다. 스쿼트 없는 루틴도 CaptureMeta를 저장한다. 시작 프레임 상자가 빠진다. StrictMode에서 이중 생성된다.
- 분석 대기열(작업 6)
  - dispose 경계, failed 영구(다시 분석 UI 없음), R1에서 포기한 key는 다음 실행 때, App 연결 테스트 없음.
  - 옛 세트의 blob을 반복해서 읽는다. `setTimeout`에 기대는 테스트가 있다.
- 결과 화면(작업 7·8)
  - 진행마다 모든 영상 blob을 getVideo로 읽는다. load가 겹치면 오래된 결과가 덮을 수 있다.
  - 영상 0·분석 0이면 제목만 남는다. failed+reason null, noPerson/error 문구, Summary·SessionDetail 끼움 테스트가 없다.
  - refresh가 낙관적 라벨 ref를 통째로 교체한다. 실패 A 뒤 성공 B면 저장소에 A가 남는다.
  - 동시 저장 중 A 실패가 B의 낙관적 변경까지 되돌린다. 메모 blur 저장이 빠질 수 있다.
  - 자동 재생이 없다(위치만 이동). 일시정지 중에도 rAF가 돈다. 겹침·nearestFrame·메모 테스트가 없다.
  - 세션 비동기 저장 전에 누르면 반복 목록이 빈다.
- 설정·정리·내보내기(작업 9~11)
  - 기록별 영상 삭제 뒤 FormFindings가 갱신되지 않는다.
  - getSettings→putSettings 덮어쓰기 경합(동시에 열리는 화면은 없다). guideSeen은 마운트 기준 운동당 1회다.
  - 동의 토글 때 영상 안내를 거치지 않는다. 부정 검증 테스트가 `setTimeout(10)`에 기댄다.
  - view.ended 시점에 세션 저장이 안 끝났으면 정리가 한 번 늦어진다.
  - failed 분석도 "분석됨"으로 보아 클립 없이 삭제한다(테스트 없음).
  - clipCutter 타이머가 play 전에 시작해 클립이 짧아질 수 있다. getVideo를 두 번 읽는다.
  - Data 폴백 문구에 영문 오류 원인이 섞인다. 동의인데 버전이 null이면 빈 문자열로 내보낸다.
  - exportFile 테스트가 없다. 미사용 구조분해 변수가 있다.
  - WorkoutFlow 연결의 통합 테스트가 없다.

## 4. 실기기 확인 (사용자, S23)
APK는 로컬에서 빌드한 것을 쓴다(모델 파일은 저장소에 없다). 설계 12절의 첫 위험부터 본다.

### 4-1. 작업 12 점검 목록
1. 녹화하면서 lite 실시간 세기가 밀리지 않는지(설계 12절 첫 위험).
2. 쉬는 시간 60초 안에 30초 세트 분석이 끝나는지, 분석 중 세기가 밀리지 않는지(설계 8절 2번).
3. 무릎이 보이는 옷·운동화로 20회 정답 영상을 찍어 설계 8절 1번 정확도 기준을 본다.
4. 맞아요/틀려요·직접 라벨이 앱을 다시 켜도 남는지. 내보낸 JSONL을 adb로 가져와 Python에서 읽히는지.
5. 4회째 기록 뒤 1회째 영상이 지적 구간만 남는지. 발열·배터리.

### 4-2. 작업별 보고에서 모은 항목
- 녹화(작업 5): MediaRecorder 코덱 선택, `video.srcObject` 스트림, 정지 시 마지막 청크가 들어가는지. 영상이 첫 상자보다 몇 프레임 늦게 시작해도 문제 없는지.
- 분석(작업 6)
  - `videoFrameReader`: MediaRecorder webm(길이 Infinity)에서 길이가 확정되는지, 15fps 시킹 속도(세트 1개 분석 시간), 시킹 뒤 canvas에 올바른 프레임이 나오는지(Android WebView).
  - 분석 중 다음 세트를 시작하면 실제로 멈추고 세기가 밀리지 않는지, 쉬는 시간에 다시 도는지.
  - 앱을 다시 켠 뒤 resumePending이 미분석 세트를 이어서 분석하는지.
  - 동적 import된 rtmposeOrt 청크와 `/form/ort/` wasm이 APK에서 CSP(wasm-unsafe-eval 등)·경로 문제 없이 로드되는지. 이 APK에는 해시 이름의 중복 wasm이 없고 `form/ort/*.wasm`만 들어 있다.
- 다시 보기(작업 8)
  - 실제 webm에서 시작 1초 전 이동이 정확한지, 메타데이터 전 `currentTime` 설정이 모바일에서 먹는지.
  - `object-fit: contain` 레터박스에서 관절 선과 영상이 어긋나지 않는지.
  - Summary에서 겹침 화면 스크롤·돌아가기, 느리게 보기 중 구간 전환.
- 보관 정리(작업 10)
  - clipCutter가 실제로 구간만 녹화하는지, 길이가 [시작-1초, 끝+1초]에 가까운지, RepPlayer에서 맞는 위치에서 시작하는지.
  - webm 길이 Infinity 영상에서 시킹/ended 동작. `captureStream`이 없으면 null이라 전체 영상을 유지하는지.
  - 클립 녹화가 실시간이라 클립당 몇 초 걸린다(백그라운드 진행). 앱이 백그라운드이면 재생이 멈춰 길이가 부정확할 수 있다.
- 내보내기(작업 11)
  - Documents에 `wom-train-*.jsonl`이 저장되는지, adb pull로 가져와 한 줄씩 JSON으로 읽히는지. 실패하면 앱 전용 폴더 폴백 문구와 경로.
  - 웹/Electron에서 objectURL 즉시 revoke가 다운로드를 끊지 않는지.

### 4-3. PC(Electron)
- 우선순위가 낮다(PC 앞에서 운동할 일이 없다). 자가 점검에 RTMPose 세션 생성 항목을 넣었지만 Electron에서는 돌려 보지 않았다.

## 5. 통합 확인 결과 (작업 12, 2026-11-24)
- `npm test -w packages/core` 356개, `npm test -w apps/app` 298개 통과. 두 패키지 typecheck와 `npm run build -w apps/app` 통과.
- Android: `cap sync`가 `@capacitor/filesystem@8.1.5`를 잡았다(플러그인 3개). `assembleDebug` 성공, `check-apk-perms.sh` 통과(INTERNET 없음, allowBackup=false).
- APK 크기 84,570,373바이트(약 80.7MiB). `public/form/rtmpose-m.onnx`(약 53MiB)와 `public/form/ort/`의 wasm 2개(jsep 21.7MB, 일반 11.2MB)가 들어 있고, 해시 이름의 중복 ORT wasm은 없다.
