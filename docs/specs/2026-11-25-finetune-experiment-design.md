- 작성일: 2026-11-25

## 0. 왜 하는가

사용자는 이 프로젝트에서 **AI 파인튜닝을 직접 해 보는 것**이 목표다. [확정] 지금은 실기기 확인을 할 수 없는 상황이라, 지금 손에 있는 데이터로 파인튜닝 실험을 먼저 한다. [확정]

이 실험은 **배포를 신경 쓰지 않는 실험용**이다. [확정] 결과 모델을 앱에 넣지 않는다. 목적은 두 가지다.
1. 파인튜닝의 대표 단계(머리만 학습 → 일부 풀기 → 전체)를 직접 해 보고, 단계마다 무엇이 달라지는지 숫자로 본다.
2. 지금 앱의 규칙 판정과 비교해서, 학습한 모델이 실제로 더 나은지 확인한다.

## 1. 범위

### 목표
1. **방식 B**: 미리 학습된 골격 동작 모델 **MotionBERT**(경량판)에 운동별 분류 머리를 붙여 파인튜닝한다. [확정]
2. **스쿼트가 본 목표**다. 학습하고, 사용자 본인 녹화로 평가하고, 규칙 판정과 비교한다. [확정]
3. **런지·플랭크 머리를 덤으로** 붙인다. '공통 몸통 + 운동별 머리' 구조가 되는지, 운동을 늘릴 때 머리만 더하면 되는지 확인한다. 평가는 EC3D의 학습에 쓰지 않은 피험자로만 한다. [확정]
4. 비교 기준 두 가지를 같은 평가 데이터로 함께 잰다. [확정]
   - 지금 앱의 **규칙 판정**(`@wom/core`의 `computeSquatRepMetrics` + `judgeSquat`)
   - **방식 A**: 같은 입력으로 처음부터 학습한 작은 시계열 모델(1D-CNN 또는 GRU)
5. 결과를 한 장의 비교 표와 짧은 보고서로 남긴다.

### 하지 않는 것 (non-goals)
- 앱에 모델 넣기, ONNX 변환, 폰 속도 측정. 이번에는 PC 실험만 한다.
- 상업 이용. MotionBERT 공개 가중치와 EC3D는 상업 조건이 불확실하므로 이번 결과는 실험용으로만 남긴다.
- 스쿼트·런지·플랭크 말고 다른 운동.
- 사전 학습부터 다시 하기(방식 C). FLEX·QEVD 같은 큰 데이터를 받은 뒤에 한다.
- FLEX·Fitness-AQA. 승인 메일이 아직 오지 않았다. 오면 같은 파이프라인에 데이터만 더한다.

### 실패로 보는 것 (anti-goals)
- **평가 오염**: 평가에 쓸 사람(EC3D 4번 피험자, 사용자 본인 녹화)의 데이터가 학습에 섞이는 것. 점수가 좋아 보여도 의미가 없다.
- **개인 데이터 유출**: 사용자 본인 녹화(관절 좌표·영상)가 git에 들어가거나 PC 밖으로 나가는 것.
- 숫자 없이 "잘 된다"고 말하는 것. 모든 비교는 같은 평가 데이터의 같은 지표로 한다.

## 2. 제약

- **PC에서만**. GPU는 RTX 4060 Ti 8GB, Windows, Python 3.11. 학습 데이터와 결과는 PC 밖으로 보내지 않는다.
- **다운로드는 사용자 허락 뒤에**: PyTorch(CUDA판, 약 2.5GB)와 필요한 Python 패키지, MotionBERT 코드와 경량 사전학습 가중치, EC3D 데이터, Zenodo 데이터.
  - MotionBERT 가중치는 OneDrive 링크로 배포된다. 자동으로 받을 수 없으면 사용자가 브라우저로 받아 정해진 폴더에 넣는다. **[확인 필요]**
- 작업 위치: 저장소 안 `ml/` 폴더. **코드는 커밋하고, 데이터·가중치·가상환경·결과 파일은 `.gitignore`로 뺀다.** [제안]
- 사용자 본인 녹화는 지금 있는 자리(`packages/core/test/fixtures/private/angle-test/`, git 제외)에서 읽기만 한다. 복사본을 만들면 `ml/data/` 같은 git 제외 폴더에만 둔다.
- 라이선스: EC3D는 저장소에 라이선스가 없고, MotionBERT 가중치는 비상업 데이터(Human3.6M, AMASS)로 학습됐다. **실험용으로만** 쓰고 결과 모델을 배포하지 않는다. Zenodo 스쿼트는 CC BY 4.0이다.

## 3. 데이터

| 데이터 | 형식 | 운동 | 라벨 | 용도 |
|---|---|---|---|---|
| EC3D | 3D 관절 25점, 프레임 시퀀스 | 스쿼트 132, 런지 127, 플랭크 103 시퀀스(피험자 4명) | 스쿼트: 정상, 발 너무 넓음, 무릎 모임, 깊이 부족, 상체 숙임 / 런지: 정상, 깊이 부족, 무릎이 발끝 넘음 / 플랭크: 정상, 허리 꺾임, 등 굽음 | 학습(피험자 1~3), 평가(피험자 4) |
| Zenodo 18859797 | MediaPipe 2D 관절 + 엉덩이·무릎 각도 | 스쿼트(22명) | 표준, 얕게, 굿모닝 | 학습 |
| 사용자 본인 녹화 | ① MediaPipe lite 33점(3D world + 2D image) 4건, ② 영상 1건을 RTMPose-m(Halpe26 2D)으로 뽑은 것 | 스쿼트 약 50회 | 녹화할 때 순서를 정해 두고 했으므로 시간 구간으로 정답을 붙인다(아래) | **평가 전용** |

사용자 본인 녹화의 정답 [확정: 녹화 때 정한 순서]
- 45도 12회 녹화: 1~4 바른 자세, 5~8 무릎 모으기, 9~12 무릎 앞으로(앱 기준으로는 오류 아님 → '정상'으로 본다)
- 영상 20회: 1~4 바른 자세, 5~8 무릎 모으기, 9~12 뒤꿈치 들기, 13~16 빨리 내려가기(자세 오류 아님 → '정상'), 17~20 얕게 앉기
- 옆·정면·45도 6회 녹화: 1~2 바른 자세, 3~4 무릎 모으기, 5~6 무릎 앞으로
- 반복 구간을 찾는 방법과 정확한 시각은 `docs/specs/2026-11-24-form-analysis-design.md` 10절 시험과 같게 한다(무릎 각도로 반복 찾기). 영상 20회의 바닥 시각은 core의 개인 회귀 테스트(`packages/core/test/squatRules.test.ts`)에 적힌 20개 값을 쓴다.

### 3.1 라벨 맞추기 [제안]
운동마다 **오류별 이진 라벨(있다/없다) 여러 개**로 맞춘다(한 반복에 오류가 둘 있을 수 있으므로). 정상은 '오류가 하나도 없음'이다.

| 머리 | 오류 칸 | 데이터별 연결 |
|---|---|---|
| 스쿼트 | `kneeIn`(무릎 모임), `shallow`(깊이 부족), `feetWide`(발 너무 넓음), `trunkLean`(상체 과다 숙임) | EC3D 무릎 모임→kneeIn, 깊이 부족→shallow, 발 너무 넓음→feetWide, 상체 숙임→trunkLean / Zenodo 얕게→shallow, 굿모닝→trunkLean / 본인 녹화: 무릎 모으기→kneeIn, 얕게 앉기→shallow, 나머지(바른 자세·무릎 앞으로·빨리)→모두 0. **뒤꿈치 들기는 공개 데이터에 라벨이 없으므로 평가에서 빼고, 그 반복의 다른 칸만 평가한다** |
| 런지 | `shallow`, `kneeOverToe` | EC3D 그대로 |
| 플랭크 | `archedBack`, `hunchBack` | EC3D 그대로 |

- 앱이 판정하는 오류(kneeIn, shallow)가 **주 지표**다. feetWide·trunkLean은 학습에는 쓰되 본인 녹화에는 그런 반복이 없어서, 본인 녹화 평가에서는 "잘못 지적하지 않는지"만 본다.

### 3.2 입력 맞추기 [제안]
- 모든 데이터를 **MotionBERT 입력 형식(H36M 17점 2D + 신뢰도)**으로 바꾼다. 골반 중심, 척추, 가슴, 목, 머리처럼 원본에 없는 점은 주변 점(양 골반 중점 등)으로 계산한다.
- EC3D(3D)는 **가상 카메라로 2D에 투영**한다. 앱 조건(45도)에 가깝게 여러 방향(예: 0°, 30°, 45°, 60°, 90°)으로 투영해 학습 데이터를 늘린다. 이게 공개 데이터와 우리 촬영 각도의 차이를 줄이는 핵심 장치다.
- 반복 하나를 고정 길이로 맞춘다(예: 길이 T로 다시 샘플링). 좌우 반전, 작은 회전·크기 변화, 속도 변화로 데이터를 늘린다.
- 좌표는 사람 크기로 나눠 정규화한다(거리 절댓값을 쓰지 않는다는 앱 원칙과 같다).
- 본인 녹화도 같은 변환을 거친다(MediaPipe 33점 → H36M 17점, RTMPose Halpe26 → H36M 17점).

## 4. 실험 순서

```
데이터 받기·변환 → 규칙 판정 점수 → 방식 A(처음부터) 점수
→ MotionBERT ① 몸통 고정, 머리만 학습(linear probe)
→ ② 몸통 뒷부분 몇 층 풀기(부분 파인튜닝)
→ ③ 전체를 작은 학습률로(전체 파인튜닝)
→ 런지·플랭크 머리 추가(몸통은 ③에서 만든 것 그대로 두고 머리만 학습) → 비교 표·보고서
```
- 모든 단계는 **같은 학습/평가 분할, 같은 지표**로 잰다.
- 무작위 시드를 고정하고, 가능하면 시드 3개로 반복해 평균과 편차를 적는다(데이터가 적어서 흔들림이 크다). [제안]

## 5. 평가

- **분할** [확정]
  - EC3D: 피험자 1~3 학습, 피험자 4 평가(EC3D 논문과 같음).
  - Zenodo: 학습에만 쓴다. 검증용으로 사람 단위로 일부를 떼어 써도 된다(같은 사람이 학습과 검증에 함께 들어가면 안 됨).
  - 사용자 본인 녹화: **평가 전용**. 학습·검증·하이퍼파라미터 고르기에 쓰지 않는다.
- **지표** [제안]: 오류 칸마다 정밀도·재현율·F1, 그리고 앱 합격 기준과 같은 형태로 "일부러 만든 오류 반복을 몇 개 잡았나 / 오류 없는 반복을 몇 개 잘못 지적했나".
- 규칙 판정은 학습이 없으므로 본인 녹화에서만 잰다(EC3D 4번에도 돌릴 수 있으면 함께, **[확인 필요]**: 3D→2D 투영본에서 규칙 판정이 의미 있는지).

## 6. 결과물

- `ml/` 아래 Python 코드(데이터 변환, 학습, 평가 스크립트)와 실행 방법(README).
- 결과 보고서 `docs/finetune-experiment-results.md`: 비교 표(규칙 / A / B①②③, 본인 녹화·EC3D 4번), 단계별로 무엇이 달라졌는지, 런지·플랭크 머리 결과, 해석과 다음에 할 것. **개인 녹화의 원본 수치나 좌표는 옮기지 않고 집계 지표만 쓴다.**
- 학습된 가중치와 중간 산출물은 git 밖(`ml/runs/` 등)에만.

## 7. 빌더에게 맡기는 것

- MotionBERT 경량판의 정확한 설정(입력 길이, 머리 구조, 학습률, 몇 층을 풀지, 에폭).
- H36M 17점 변환 공식, 가상 카메라 투영 방식, 데이터 늘리기 세부.
- 방식 A의 모델 구조.
- 스크립트 구조와 설정 파일 형식.
- EC3D 시퀀스가 반복 여러 개를 담고 있으면 반복으로 자르는 방법, Zenodo 파일 구조 해석(받아 본 뒤 정한다).

## 8. 위험

| 위험 | 대응 |
|---|---|
| 데이터가 적어(EC3D 4명) 과적합 | 머리만 학습(①)을 먼저 하고, 시드 여러 개로 흔들림을 본다. 데이터 늘리기 |
| 공개 데이터와 앱 조건(45도, RTMPose)이 달라 본인 녹화 점수가 낮음 | 가상 카메라 투영으로 각도 차이를 줄인다. 낮게 나오면 그 자체를 결과로 적는다 |
| 관절 형식 변환 오류 | 변환 뒤 몇 개를 그림으로 그려 눈으로 확인한다(그림은 git 밖) |
| MotionBERT 가중치를 자동으로 못 받음 | 사용자가 브라우저로 받아 넣는다 |
| 8GB VRAM 부족 | 경량판, 작은 배치, 혼합 정밀도 |
| 본인 녹화가 너무 적어(약 50회) 평가가 거칠다 | 결과를 '방향 확인' 수준으로 해석하고, 실기기에서 정답 영상이 더 모이면 다시 잰다 |
