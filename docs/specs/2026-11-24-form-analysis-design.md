## 0. 왜 만드는가

지금 앱은 횟수와 시간만 센다. 사용자는 운동이 끝난 뒤 **"어디가 부족했는지"**를 알고 싶어 한다. 예를 들면 "2세트 4번째 반복(0:18)에서 무릎이 안으로 모였어요" 같은 안내다. 그리고 그 순간을 **실제 영상으로 다시 보고** 싶어 한다. [확정]

사용자는 운동하는 동안 지적받는 것이 아니라, 운동이 끝난 뒤 결과 화면에서 돌아보는 것을 원했다. [확정]

## 1. 범위

### 목표
1. 세트를 하는 동안 카메라 영상을 폰 안에만 녹화한다. [확정]
2. 세트가 끝나면 저장한 영상을 정확도가 높은 자세 모델 **RTMPose-m**(Halpe26, 발 점 포함)으로 다시 분석한다. [확정: 비교 시험 뒤 결정, 10절]
   - 사람 영역은 실시간으로 이미 돌고 있는 MediaPipe lite 관절점으로 잡는다. 사람 검출 모델은 따로 돌리지 않는다.
3. 반복마다 자세 오류를 판정하고, 운동 결과 화면과 기록 상세 화면에 "몇 세트, 몇 번째 반복, 영상 몇 초, 무엇이 문제인지"를 보여 준다. [확정]
4. 지적 항목을 누르면 그 순간의 영상으로 이동해서 재생한다. 영상 위에 관절 선을 겹쳐 보여 주고, 켜고 끌 수 있다. [제안]
5. 영상 보관: **루틴마다 최근 3회는 전체 영상**을 남긴다. 그보다 오래된 기록은 **지적이 나온 반복 앞뒤 구간만** 남긴다. [확정]
6. 처음 대상 운동은 **스쿼트** 하나다. 다른 운동은 같은 구조에 판정 규칙만 더하는 식으로 나중에 넓힌다. [제안]
7. **파인튜닝용 학습 데이터를 모은다.** [확정] 지적마다 "맞아요 / 틀려요"를 받고, 놓친 오류를 사용자가 직접 표시할 수 있게 한다. 학습 데이터 사용 동의를 받고, 모은 데이터를 PC로 내보낸다(7.1절).
   - 사용자는 이 프로젝트에서 AI 파인튜닝을 직접 해 보는 것이 목표다. 파인튜닝 자체는 **별도 설계 문서**로 다룬다. 이 기능은 그 데이터를 모으는 도구다.
   - 지금은 **배포를 신경 쓰지 않는 실험용 파인튜닝**이 목표다. [확정] 다만 나중에 상업 출시할 가능성이 있으므로, 데이터마다 출처와 동의 여부를 기록해 나중에 상업용 학습 데이터만 골라낼 수 있게 한다.

### 스쿼트 지적 항목 [확정: 논문 조사와 시험 뒤 결정]
| 항목 | 반복마다 / 세트 요약 | 처음 버전에 넣음 |
|---|---|---|
| 깊이 부족 | 반복마다 | ✅ |
| 무릎이 안으로 모임 | 반복마다 | ✅ |
| 너무 빨리 내려감 | **세트 요약으로 한 번** (반복마다 지적하면 잔소리가 된다) | ✅ |
| 뒤꿈치 들림 | 반복마다 | ✅ RTMPose 발 점으로 측정됨(MediaPipe는 실패) |
| 골반 좌우 기울어짐 | — | ❌ 바른 자세에서도 값이 크게 흔들림 |
| 무릎이 발끝을 넘음 | — | ❌ **지적하지 않는다**. 오류가 아니라는 근거가 있다(9절) |
| 허리 말림, 머리·가슴 자세 | — | ❌ 관절점으로 재기 어렵고 근거도 엇갈림 |

### 하지 않는 것 (non-goals)
- 운동 중 실시간 자세 지적(음성·화면). 이번에는 운동 뒤 결과 화면에서만 보여 준다.
- 서버·클라우드 처리, 영상 업로드. 영상과 관절 좌표는 폰 밖으로 나가지 않는다.
- 이 기능 안에서의 ML 모델 학습. 앱의 판정은 RTMPose 관절점과 각도·비율 규칙으로 한다. 학습은 PC에서 별도 프로젝트로 한다.
- 운동 12종 추가(바벨 벤치프레스, 딥스 등). 이 작업이 끝난 뒤 **별도 프로젝트**로 한다.
- PC(Electron)에서의 동작 보장. 웹 코드라 돌아갈 수는 있지만 목표가 아니다. 사용자가 PC 앞에서 운동하지 않는다.

### 실패로 보는 것 (anti-goals)
- **틀린 지적.** 잘못 지적하는 것은 지적하지 않는 것보다 나쁘다. 정확도를 재서 기준을 넘은 항목만 내보낸다(8절).
- 운동 흐름을 방해하는 것. 분석이 늦어져도 횟수 세기, 쉬는 시간, 음성 안내가 느려지면 안 된다.
- 영상이 폰 밖으로 나가는 것. 네트워크 요청 0건 원칙을 지킨다.

## 2. 제약

- **네트워크 0건, 서버 없음.** 기존 원칙을 그대로 따른다. Android INTERNET 권한 없음, allowBackup=false, CSP 유지.
- 기준 기기: 갤럭시 S23. 앱은 Capacitor WebView에서 돈다.
- 실시간 횟수 세기는 지금처럼 **lite** 모델로 한다. 바꾸지 않는다.
- 측정된 S23 속도(Chrome, 1080×1920 영상)
  - MediaPipe: 프레임당 lite 30ms, full 36ms, heavy 66ms
  - **RTMPose-m**(ONNX Runtime Web 1.20.1): WebGPU 중앙값 70ms(평균 111ms, 가끔 튐), WASM 106ms(일정). 크롭·정규화 전처리 16~22ms 별도
  - 15fps로 30초 세트(450프레임)를 분석하면 약 45~60초가 걸린다.
- 새 의존성: `onnxruntime-web`(MIT), RTMPose-m 모델 파일(약 56MB, APK 크기가 그만큼 커진다).
- 영상과 관절 좌표는 개인 신체 데이터다. 앱 전용 저장소에만 두고 갤러리에는 넣지 않는다. [제안]
- 기존 기록(WorkoutSession)과 호환돼야 한다. 영상이 없는 옛 기록도 지금처럼 보여야 한다.

## 3. 촬영 방법 [확정: 시험 뒤 결정]

- **45도 한 방향.** 폰을 몸 앞쪽 대각선, 허리 높이에 두고 머리부터 발끝까지 여유 있게 나오게 한다.
  - 옆에서는 무릎 모임이 안 보이고, 정면에서는 손이 골반을 가릴 때 무릎 점이 튄다. 45도가 둘 다 가장 나았다(10절).
- 배치 안내 화면(Placement)을 운동별로 바꾼다. 스쿼트는 "45도, 허리 높이, 발끝까지 화면에"로 안내한다.
- 옷차림 안내를 추가한다.
  - **무릎 윤곽이 보이는 옷**(반바지나 몸에 붙는 운동복 바지)
  - **신발은 평소대로 신어도 된다** [확정]. 맨발일 필요는 없다.
  - 팔은 앞으로 뻗거나 가슴 앞에 모은다(골반을 가리지 않게).
- 이 안내는 처음 몇 번만 보여 주고, "다시 보지 않기"를 둔다. [제안]

## 4. 전체 흐름

```
세트 시작 ─▶ 영상 녹화 시작 (lite 실시간 세기는 지금 그대로)
세트 끝   ─▶ 녹화 종료, 영상 파일 저장 (세트당 파일 1개) [제안]
         ─▶ 분석 대기열에 넣음
쉬는 시간 ─▶ 대기열을 RTMPose-m으로 분석 (실시간 세기와 음성은 늘 우선)
루틴 끝   ─▶ 남은 분석을 계속하고, 결과 화면에 "분석 중…" → 끝나면 지적 목록을 채움
기록 상세 ─▶ 지적 목록 → 누르면 해당 시각으로 영상 재생
```

### 4.1 반복 목록은 실시간 카운터를 기준으로 한다 [제안]
- "4번째 반복"은 사용자가 운동 중에 들은 숫자와 같아야 한다. 그래서 **분석은 반복을 새로 찾지 않는다.** 실시간 카운터(lite)가 확정한 반복의 시작·끝 시각을 그대로 쓰고, 그 구간 안에서 RTMPose 관절점으로 지표만 계산한다.
- 이를 위해 기록(SetLog)에 **반복마다 시작·바닥·끝 시각**을 추가로 저장한다. 지금 SetLog에는 반복 시각이 없다. 기존 기록은 이 필드가 없어도 읽혀야 한다.
- 영상의 시작 시각과 세트 시각을 같은 시계로 맞춰 둔다. 그래야 "반복 시각 → 영상 몇 초"로 바꿀 수 있다.

### 4.2 분석 속도 [제안]
- 영상을 **15fps로(한 프레임씩 건너뛰며)** 분석한다. 30초 세트면 약 45~60초다. 깊이와 무릎 각도는 1초에 15장이면 충분하다.
- WebGPU를 먼저 쓰고, 안 되거나 느리면 WASM으로 바꾼다. [제안]
- **사람 영역**: 실시간 세기 때 저장해 둔 MediaPipe lite 관절점을 감싼 상자를 그대로 넘긴다(RTMPose 기본 여유 1.25배). 상자를 임의로 더 넓히지 않는다. 시험에서 15% 넓혔을 때 빠른 반복 2회가 무릎 모임으로 잘못 나왔다. [확정: 시험 결과]
  - 이를 위해 세트 동안 lite 관절점(또는 프레임별 상자)을 영상과 함께 저장한다.
- 분석은 쉬는 시간에 한다. 다 못 끝내면 다음 쉬는 시간이나 루틴이 끝난 뒤에 이어서 한다.
- 앱이 중간에 꺼져도 다음에 열었을 때 남은 분석을 이어서 한다. [제안]
- 실시간 세기(lite)와 RTMPose 분석을 동시에 돌릴 때의 성능, 앱(WebView) 안에서의 속도는 **[확인 필요]**이다. 세기가 밀리면 분석을 멈춘다.

## 5. 판정 규칙 (스쿼트)

공통 전처리 [제안]
- RTMPose의 **2D 화면 좌표**(Halpe26: 엉덩이·무릎·발목·엄지발가락·뒤꿈치 등 26점)를 쓴다. 3D 좌표는 쓰지 않는다. 45도 촬영에서는 2D 각도와 비율만으로 세 항목이 모두 갈렸다(10절).
  - 카메라 한 대로는 실제 거리를 알 수 없다. MediaPipe의 3D 좌표도 미터 단위로 나오지만 추정값일 뿐이다. [확정]
  - 그래서 판정에는 **거리의 절댓값(cm)을 쓰지 않는다.** 각도와 비율(무릎 간격 ÷ 발목 간격처럼 같은 프레임 안 길이끼리의 비)만 쓴다.
  - 사용자에게도 cm 같은 거리 숫자를 보여 주지 않는다.
  - 판정이 맞는지는 측정값의 정밀도가 아니라 **판정 결과가 정답(일부러 만든 오류, 사용자 라벨)과 맞는지**로 검증한다(8절).
- 인식이 틀린 프레임을 버린다. 관절이 안 잡힌 프레임이나, 허벅지·정강이 길이가 그 세트의 중앙값과 크게 다른 프레임이다.
- 반복의 바닥 시각 앞뒤 150ms 구간의 **중앙값**으로 판정한다. 한 프레임 값으로 판정하지 않는다.
- 양쪽 다리 값을 함께 본다. 한쪽 다리만 굽힌 동작(발 옮기기)은 반복으로 세지 않는다. 이건 실시간 카운터의 몫이지만, 분석에서도 한쪽만 굽은 구간은 판정하지 않는다.

### 5.1 깊이 부족
- 지표: 바닥에서의 무릎 안쪽 각도(엉덩이–무릎–발목, 2D 화면 각도, 양쪽 평균). 45도 촬영이라 실제 각도와 다르다. 판정용으로만 쓰고 화면에 각도 숫자를 보여 주지 않는다.
- 기준: 허벅지가 바닥과 최소 평행(평가표 9번). 시험에서 RTMPose-m은 일부러 얕게 앉은 반복이 109~118°, 나머지가 89° 이하였다. **처음 기준값은 100°**로 둔다. 이 값보다 크면 "깊이 부족"이다. [제안, 확인 필요]
- 문구 예: "4번째: 허벅지가 바닥과 평행해질 때까지 앉지 않았어요"

### 5.2 무릎이 안으로 모임
- **바른 자세 등록은 하지 않는다.** [확정] 사용자가 바른 자세를 모를 수 있고, 틀린 자세로 등록하면 그게 기준이 되어 오류를 영영 못 잡는다.
- 지표: 바닥에서의 **무릎 간격 ÷ 서 있을 때 발목 간격**(2D 화면 거리)
  - 발은 스쿼트 동안 움직이지 않으므로, 세트 안에서 서 있는 프레임의 발목 간격 중앙값을 '발 너비'로 쓴다.
  - 사용자는 편하게 서 있기만 하면 된다.
- 두 기준을 함께 쓴다. [확정]
  - **① 절대 기준(주 기준)**: 값이 **0.9 미만**이면 지적한다. 무릎이 발보다 안쪽으로 들어온 것이고, 평가표 5번("무릎이 복사뼈 안쪽 선을 넘지 않음")에 해당한다. 문구 예: "6번째: 무릎이 발보다 안쪽으로 모였어요"
    - **0.9~1.1은 '확실하지 않음'으로 보고 지적하지 않는다.** [제안] 기준값 하나에 판정이 걸려 있어서 경계 근처에서 잘못 지적하는 것을 막는다. 학습 데이터에는 값과 함께 남긴다.
    - RTMPose-m 시험에서 무릎 모으기 반복은 0.59~0.73, 나머지는 1.24 이상이었다.
  - **② 상대 기준(보조)**: ①에 걸리지 않은 반복 중 값이 '평소의 나'보다 **15% 이상** 낮으면 지적한다. 문구 예: "8번째: 평소보다 무릎이 모였어요"
    - '평소의 나'는 이번 세트와 최근 기록의 같은 운동에서, **비슷한 깊이(바닥 무릎 각도 ±10°)로 앉은 반복** 값의 중앙값이다. [제안]
    - 비교할 반복이 5개 미만이면 ②는 판정하지 않는다. [제안]
    - 피로로 세트 뒤쪽에 무릎이 무너지는 흔한 경우를 잡는다.
- 깊이가 부족한 반복은 원래 무릎이 덜 벌어지므로 무릎 모임을 판정하지 않고 '깊이 부족'만 지적한다.
- 한계: 늘 조금씩 무릎이 모이는 사람은 ①에 걸리지 않으면 ②로도 잡히지 않는다('평소'가 이미 모인 상태). 이 한계는 문서로 남기고 받아들인다.
- 시험 근거(10절): MediaPipe 3D로는 녹화마다 바른 자세 값이 1.16~2.21로 달라 상대 기준이 필요했다. RTMPose-m 2D로는 절대 기준만으로 깔끔하게 갈렸다. 0.9, 1.1, 15%는 [확인 필요]이다.
- 발 방향(무릎이 발끝을 따라가는지)은 이번에는 쓰지 않는다. RTMPose 발 점으로 다시 시험해 볼 수 있다. [확인 필요]

### 5.3 뒤꿈치 들림
- 지표: (엄지발가락 높이 − 뒤꿈치 높이) ÷ 정강이 길이(2D, 양발 평균). 바닥에서의 값에서 서 있을 때 값을 뺀다. 클수록 뒤꿈치가 발가락보다 많이 들린 것이다.
- 기준: 평가표 7번("발 전체가 바닥에 닿음"). 시험에서 RTMPose-m은 뒤꿈치를 든 반복이 0.31~0.47, 나머지는 0.21 이하였다. **처음 기준값은 0.25**로 둔다. [제안, 확인 필요]
- 문구 예: "10번째: 뒤꿈치가 바닥에서 떨어졌어요"
- 뒤꿈치가 들리는 건 발목이 덜 굽혀져서 생기는 경우가 많다. 안내 문구에 "발 전체로 바닥을 누르세요" 정도만 붙인다. [제안]
- OpenCV 옵티컬 플로우로 뒤꿈치를 추적하는 방법은 빠른 동작에서 틀어져서 쓰지 않는다.

### 5.4 너무 빨리 내려감 (세트 요약)
- 지표: 반복마다 내려가는 시간(서 있는 각도에서 15° 내려간 시점부터 바닥까지)과 올라오는 시간.
- 기준: 내려가는 데 2~3초를 권장한다(Schoenfeld 2010). 평가표는 내려가는 시간이 올라오는 시간의 2배 이상이어야 한다고 본다(Myer 2014).
- 세트 평균 내려가는 시간이 **1초 미만**이면 세트 요약에 한 줄로 알려 준다. [확정 2026-11-25: 사용자가 템포 코칭으로 그대로 두기로 함. 바닥 시각을 실제 최저점으로 고친 뒤 평소 속도 0.5~1.1초라 자주 뜨는 것을 알고 결정]
  - 예: "이번 세트는 평균 0.6초 만에 내려갔어요. 2초 이상 천천히 내려가 보세요"
- 사용자가 평소에도 0.6~0.8초에 내려가서, 반복마다 지적하면 모든 반복이 걸린다. 그래서 요약으로만 알려 준다.

### 5.5 판정하지 않는 것을 화면에 쓰지 않는다
- 무릎이 발끝을 넘는 것은 지적하지 않는다. 다만 "이번 세트는 엉덩이 위주 / 무릎 위주였어요" 같은 참고 정보로 보여 줄지는 나중에 정한다.

## 8. 합격 기준

1. **정확도** (사용자 본인 영상, 45도, 무릎이 보이는 옷과 운동화)
   - 바른 자세, 무릎 모으기, 뒤꿈치 들기, 얕게 앉기, 빨리 내려가기가 섞인 20회 영상에서 다음을 만족해야 한다.
     - 깊이 부족, 무릎 모임, 뒤꿈치 들림: 일부러 만든 오류 반복을 **모두** 지적한다.
     - 해당 오류가 없는 반복을 잘못 지적한 것이 **1회 이하**다. 특히 빠르게 내려간 반복을 무릎 모임으로 잘못 지적하지 않아야 한다.
   - 기준을 넘지 못한 항목은 내보내지 않는다(설정에서 숨김). 
2. **속도**: S23 앱에서 30초 세트 분석이 다음 세트가 시작되기 전(쉬는 시간 60초 기준)에 끝난다. 분석 중에도 실시간 세기가 프레임을 놓치지 않는다.
3. **보관**: 4회째 기록이 저장되면 1회째 기록 영상이 지적 구간만 남는다. 지운 구간을 누르면 안내 문구가 나온다.
4. **개인정보**: 네트워크 요청 0건(자가 점검 유지), 영상이 갤러리에 나타나지 않는다, 백업에 포함되지 않는다.
5. **호환**: 영상과 반복 시각이 없는 기존 기록도 지금처럼 열린다.
6. **정답 수집**: 지적에 맞아요/틀려요를 누르고, 놓친 오류와 정상 표시를 붙일 수 있다. 앱을 다시 켜도 라벨이 남아 있다.
7. **동의와 내보내기**: 동의한 기록만 내보내기 파일에 들어간다. 동의를 끈 뒤의 기록은 빠진다. 내보낸 파일을 adb로 PC에 가져와 Python에서 읽을 수 있다. 내보내기 중 네트워크 요청은 0건이다.

## 9. 근거 자료 요약

- Myer 등 2014, 스쿼트 평가표(10개 항목) [PMC4262933]: 몸통과 정강이가 나란함, 무릎이 복사뼈 안쪽 선을 넘지 않음, 발 전체가 바닥에 닿음, 허벅지가 최소 평행, 내려가는 시간이 올라오는 시간의 2배 이상. 무릎 전진은 뒤꿈치가 붙어 있으면 제한하지 말라고 한다.
- Straub & Powers 2024 리뷰 [PMC10987311]: 몸통과 정강이 기울기는 엉덩이와 무릎 부하를 맞바꾼다. 몸통–정강이 각도가 −8°면 엉덩이와 무릎 부하가 비슷하다. 최적 스탠스는 정해져 있지 않다.
- Fry 2003: 무릎 전진을 막으면 엉덩이 토크가 크게 늘었다(7명, 작은 연구).
- 무릎 외반 연구: 서 있을 때보다 10° 이상 안으로 꺾이면 외반으로 본다. 2D 측정의 신뢰도는 괜찮지만 3D와 비교하면 정확도에 한계가 있다.
- Schoenfeld 2010: 내려가는 데 2~3초를 권장한다. 피로하면 자세가 무너진다.
- 2013 Sports Medicine 리뷰: 깊은 스쿼트가 연부조직 부상 위험을 늘리지 않는다.

  - MediaPipe 중에서는 깊이와 무릎 모임이 **heavy에서만** 깔끔하게 갈렸다. full은 lite보다 나은 점이 없었다.
  - 뒤꿈치 들림은 MediaPipe 세 모델 모두 잡지 못했다. 골반 기울기는 잡음이 컸다.
  - **RTMPose-m(2D, 발 점 포함)은 깊이, 무릎 모임, 뒤꿈치 들림을 모두 겹침 없이 갈랐다.**

    | 지표 | 해당 오류 반복 | 나머지 |
    |---|---|---|
    | 깊이(무릎 각도) | 얕게 109~118° | 89° 이하 |
    | 무릎÷발목 | 무릎 모으기 0.59~0.73 | 1.24 이상 |
    | 뒤꿈치 | 뒤꿈치 들기 0.31~0.47 | 0.21 이하 |

  - RTMPose-x는 PC CPU에서 3.3배 느리고 구분력은 비슷했다. m을 쓴다.
  - 사람 검출 모델(YOLOX) 대신 MediaPipe lite 관절점으로 영역을 잡아도 결과가 같거나 더 좋았다. 영역을 15% 넓히면 빠른 반복 2회(0.73, 0.87)가 무릎 모임으로 잘못 나왔다.
  - OpenCV 옵티컬 플로우로 뒤꿈치를 추적하는 방법은 빠른 반복에서 틀어졌다.
  - S23 Chrome에서 RTMPose-m 결과는 PC 결과와 중앙값 12px(화면 높이의 0.6%) 차이였다.
  - 영상 속 옷차림(헐렁한 긴 바지, 슬리퍼)이 무릎과 발목 윤곽을 가렸다. 운동화와 운동복 바지로는 아직 시험하지 않았다. **[확인 필요]**
- 기준값(깊이 100°, 무릎 모임 0.9 미만·0.9~1.1 보류·평소보다 15%, 뒤꿈치 0.25, 속도 1초)은 한 사람, 영상 하나로 잡은 임시값이다.
- 녹화와 영상은 git 밖(`packages/core/test/fixtures/private/angle-test/`, `apps/spike/public/mediapipe/bench/`)에만 있다.

## 11. 빌더에게 맡기는 것

- 영상 녹화 방식(MediaRecorder 형식·비트레이트)과 저장 위치(IndexedDB Blob 또는 Capacitor 파일 시스템)
- 오래된 기록에서 지적 구간만 남기는 방법(다시 인코딩할지, 처음부터 반복 단위로 잘라 저장할지 등). 단, 7절 보관 규칙과 8절 합격 기준을 지켜야 한다.
- 분석 대기열 구현, 15fps 추출 방식, RTMPose 모델을 실시간 lite와 함께 올리는 방식(WebGPU/WASM 선택 포함)
- 판정 규칙의 코드 구조. 다른 운동을 쉽게 더할 수 있게 한다.
- 화면 세부 디자인
- 새 의존성이 필요하면 다운로드 전에 사용자 허락을 받는다. 이미 받아 둔 것(모두 git 제외)
  - RTMPose-m Halpe26 ONNX: `apps/spike/public/mediapipe/bench/rtmpose-m.onnx` (원본: OpenMMLab `rtmpose-m_simcc-body7_pt-body7-halpe26_700e-256x192`)
  - onnxruntime-web 1.20.1 wasm 파일: `apps/spike/public/mediapipe/ort/`
  - 전처리는 rtmlib와 같게 한다: 상자 중심 기준 1.25배 여유, 192×256 비율 맞춤, MEAN (123.675, 116.28, 103.53) / STD (58.395, 57.12, 57.375)를 BGR 순서에 적용, 출력 SimCC는 argmax ÷ 2.

## 12. 위험

| 위험 | 대응 |
|---|---|
| WebView에서 MediaRecorder로 녹화하면서 lite 실시간 세기가 느려짐 | 첫 작업으로 S23에서 측정한다. 느리면 해상도·비트레이트를 낮춘다 |
| RTMPose 분석과 실시간 세기를 동시에 돌리면 세기가 밀림 | 세기가 우선이다. 밀리면 분석을 멈추고 루틴 뒤로 미룬다 |
| WebGPU 속도가 가끔 튐(느린 10%가 164ms) | WASM(106ms, 일정)으로 바꿀 수 있게 한다 |
| 사람 영역 크기에 민감함(빠른 반복에서 무릎 점이 틀어짐) | 영역 여유를 고정하고, 무릎 모임은 0.9~1.1을 보류 구간으로 둔다. 빠른 반복이 들어간 데이터로 계속 확인한다 |
| 옷차림 차이(시험은 헐렁한 바지·슬리퍼) | 무릎이 보이는 옷과 운동화로 다시 촬영해 8절 기준을 확인한다 |
| RTMPose 공개 가중치의 학습 데이터 라이선스가 섞여 있음 | 지금은 실험용이라 괜찮다. 상업 출시 전에 다시 확인한다 |
| APK 크기 증가(모델 약 56MB) | 받아들인다. 필요하면 나중에 양자화한 모델을 시험한다 |
| 발열·배터리 | 실기기에서 루틴 하나를 끝까지 하며 확인한다 |
| 기준값이 한 사람·적은 데이터 기준 | 8절 정확도 기준으로 재확인한다. 넘지 못하면 그 항목은 내보내지 않는다 |
| 영상 용량 | 보관 규칙, 용량 표시, 저장 끄기 설정 |
